# Scaffold breakage log

Everything the acceptance hand-check turns up, one row each, written down before
anybody decides whether it matters. A discrepancy that looks harmless at the
time it is found is exactly the kind that turns out not to be, and the log costs
one line.

Each entry ends in one of two states, and no third:

- **Fixed.** The code was wrong and now is not. The fix commit goes in the last
  column.
- **Flagged blank.** Edgardly cannot stand behind the value, so the cell shows
  as missing with the flag message and a pointer to the filing to check. This is
  a legitimate outcome, not a failure to fix something: a number nobody can
  source is worse than an admitted hole. The root cause column says why.

An entry that is neither is open, and a checklist copy with an open entry
against it is not signed off. Phase 2 is done when all three copies are signed
and this table has no open rows. An empty table is a legitimate final state and
means the hand-check found nothing, which is worth recording as such rather than
leaving the file absent.

The rows below were found by the value comparison of 2026-08-05, which is the
Claude-session half of the hand-check described in PROGRESS.md's decisions log.
Every one is **open**. The session that found them does not close them: a
diagnosis is offered where there is one, and the decision about what to do is a
later session's, taken with the user. Nothing here has been fixed and no
application code was touched.

## Status

Sixteen entries, all open, from the value comparison of 2026-08-05. That
comparison covered five historical years of all three statements for Apple,
Honeywell and Kroger against the filings named in each checklist copy, so the
table is a result rather than a placeholder: the hand-check has been run over the
values and this is what it found.

By copy: six entries stand against Apple (1, 3, 4, 5, 6, 15), eight against
Honeywell (5, 6, 7, 8, 9, 10, 11, 16) and six against Kroger (2, 5, 6, 12, 13,
14). Rows 5 and 6 are against all three. No copy can be signed while any of them
is open, which is the rule this file already carried.

What they are not is uniform. Rows 1, 2, 4 and 6 are defects with a named line of
code and no defensible reading. Rows 3, 7, 9, 12 and 16 are places where a rule
the project settled deliberately produces a row that does not match the filing's
own line, and the decision each needs is whether the rule or the label should
move. Rows 13, 14 and 15 are the checklist and the record disagreeing with the
filings rather than the code doing so. Rows 8, 10 and 11 are small or filer-side
and are here because the rule of this log is to write a thing down before
deciding what it is.

Nothing was fixed in the session that found these, by design: the same hand
should not both report and close a defect.
